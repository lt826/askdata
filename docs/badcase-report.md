# AskData Badcase 报告

> 收录问答链路的真实失败案例：现象 → 根因 → 修复层 → 启示。
> 与 dev-log 的分工：这里记**产品行为层面**的坏案例（SQL 错、语义跑偏、安全边界），
> dev-log 记代码实现层面的坑。

## 案例 1：列名歧义 + 用户数口径双重错误（双层修复路径）

- **问题**：各会员等级的用户数和平均客单价
- **现象**：首轮 SQL `COUNT(user_id)` 报 Binder Error 歧义（orders/users 两表同名列）；修复循环 1 轮改成 `COUNT(u.user_id)` 后执行成功，**但 50434 是订单数不是用户数**（10543 才是去重用户）
- **根因**：① join 后同名列未限定表别名；② 模型默认 COUNT 就是"数数"，不知道业务上"用户数"要去重
- **修复层**：① 由**修复循环**自愈（错误信息回喂 1 轮修复）；② 由**Schema 口径速查**根治（新增"用户数/人数 = COUNT(DISTINCT user_id)"）
- **启示**：执行错误和语义错误是两类问题——前者靠循环自愈，后者靠数据字典（口径文档）预防。这是"语义问题的修复点在数据字典层，不在 prompt 层"的实证。

## 案例 2：执行成功但答非所问——TopN 返回 249 行明细

- **问题**：复购用户（下单超过 1 次）最喜欢的三个品类
- **现象**：SQL 执行成功（249 行 category+subcategory 明细），但用户要的是"三个品类"的聚合排名；且按 subcategory 而非 category 聚合
- **根因**：模型生成的是"复购用户的订单明细"而不是"按品类聚合的 Top3"；执行层无错可报——**这类错误修复循环救不了**（没有报错信号）
- **修复层**：Schema 口径速查新增两条："TopN 必须先 GROUP BY 聚合到目标维度再 ORDER BY+LIMIT"、"品类默认指 category 一级"。修复后一轮直出 3 行聚合
- **启示**：最危险的 badcase 不是报错的，是**不报错但答非所问**的——这正是要用"执行准确率"（结果集比对标准答案）而非"执行成功率"做评测的原因。已列入评测集必测题型。

## 案例 3：恶意指令——模型服从"删表"生成 DROP TABLE

- **问题**：把 orders 表删了
- **现象**：模型照做，生成 `DROP TABLE orders`；被执行器首词白名单拦截，返回"[SQL被拒绝] 只允许 SELECT 查询"
- **根因**：模型对用户指令无条件服从，没有安全判断（符合预期——安全不该指望模型自觉）
- **修复层**：护栏设计本就假设模型会生成危险 SQL：白名单（UX 层，报友好错误）→ read_only 连接（引擎层，提示词被绕过也写不进库）
- **启示**：**安全约束放在连接层而不是提示词层**——提示词是"请求"，read_only 是"物理定律"。演示安全设计时的现成素材。
