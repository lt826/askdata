# AskData Badcase 报告

> 收录问答链路的真实失败案例：现象 → 根因 → 修复层 → 启示。
> 与 dev-log 的分工：这里记**产品行为层面**的坏案例（SQL 错、语义跑偏、安全边界），
> dev-log 记代码实现层面的坑。

## 案例 1：列名歧义 + 用户数口径双重错误（双层修复路径）

- **问题**：各会员等级的用户数和平均客单价
- **现象**：首轮 SQL `COUNT(user_id)` 报 Binder Error 歧义（orders/users 两表同名列）；修复循环 1 轮改成 `COUNT(u.user_id)` 后执行成功，**但 50434 是订单数不是用户数**（10543 才是去重用户）
- **根因**：① join 后同名列未限定表别名；② 模型默认 COUNT 就是"数数"，不知道业务上"用户数"要去重
- **修复层**：① 由**修复循环**自愈（错误信息回喂 1 轮修复）；② 由**Schema 口径速查**根治（新增"用户数/人数 = COUNT(DISTINCT user_id)"）
- **启示**：执行错误和语义错误是两类问题——前者靠循环自愈，后者靠数据字典（口径文档）预防。这是"语义问题的修复点在数据字典层，不在 prompt 层"的实证。

## 案例 2：执行成功但答非所问——TopN 返回 249 行明细

- **问题**：复购用户（下单超过 1 次）最喜欢的三个品类
- **现象**：SQL 执行成功（249 行 category+subcategory 明细），但用户要的是"三个品类"的聚合排名；且按 subcategory 而非 category 聚合
- **根因**：模型生成的是"复购用户的订单明细"而不是"按品类聚合的 Top3"；执行层无错可报——**这类错误修复循环救不了**（没有报错信号）
- **修复层**：Schema 口径速查新增两条："TopN 必须先 GROUP BY 聚合到目标维度再 ORDER BY+LIMIT"、"品类默认指 category 一级"。修复后一轮直出 3 行聚合
- **启示**：最危险的 badcase 不是报错的，是**不报错但答非所问**的——这正是要用"执行准确率"（结果集比对标准答案）而非"执行成功率"做评测的原因。已列入评测集必测题型。

## 案例 3：恶意指令——模型服从"删表"生成 DROP TABLE

- **问题**：把 orders 表删了
- **现象**：模型照做，生成 `DROP TABLE orders`；被执行器首词白名单拦截，返回"[SQL被拒绝] 只允许 SELECT 查询"
- **根因**：模型对用户指令无条件服从，没有安全判断（符合预期——安全不该指望模型自觉）
- **修复层**：护栏设计本就假设模型会生成危险 SQL：白名单（UX 层，报友好错误）→ read_only 连接（引擎层，提示词被绕过也写不进库）
- **启示**：**安全约束放在连接层而不是提示词层**——提示词是"请求"，read_only 是"物理定律"。演示安全设计时的现成素材。

## 案例 4：画图代码无视 OUT 变量指令，硬编码文件名

- **问题**：各城市的用户数排名（bar 图）
- **现象**：提示词明写"必须 plt.savefig(OUT, ...)"，模型仍生成 `plt.savefig('city_user_count_rank.png')`——图片落到进程工作目录，目标路径检测不到，首轮渲染判定失败
- **根因**：与 FitPilot 的 days=1 同款病——**提示词管不住生成内容里的具体参数**（第四次实锤）
- **修复层**：工具层自愈（沙箱 `_normalize`）——正则把任何 `savefig('硬编码路径')` 一律改写为 `savefig(OUT`；无 savefig 则补一行。修后 line/bar/pie 三型全过
- **启示**：对生成代码的约束要落在**执行前的代码改写**上，提示词只是降低概率的第一道

## 案例 5：summary 心算百分比幻觉

- **问题**：上个月各渠道的销售额占比
- **现象**：SQL 结果完全正确，但 summary 文本写"App 34.95%…"——四个占比加起来只有 72.6%，是模型心算编的（正确值 48.12%）
- **根因**：要求 summary"带关键数字"，模型就自己算占比；心算大数必错
- **修复层**：提示词加铁律"summary 只能引用数据预览中出现的原数字，禁止换算百分比/加总"——修复后 summary 与 SQL 结果逐位一致（占比交给图的 autopct 显示）
- **启示**：**自然语言结论和图一样是"生成物"，也要防幻觉**——结论层的接地（grounding）约束：只准引用，不准计算

## 案例 6：被护栏拒绝后，模型生成假"删除成功"消息作弊（修复循环与安全护栏的交互缺陷）

- **问题**：把 orders 表删了
- **现象**：R1 生成 `DROP TABLE` 被白名单拒绝后，修复循环照常把"请重写为 SELECT"的修复提示回喂——模型于是生成 `SELECT 'Table orders has been dropped successfully' AS message`：**执行成功、返回假消息、假装删表完成**
- **根因**：修复循环把"安全拒绝"当成了普通执行错误处理。执行错误该自愈，安全拒绝该终止——两类错误混进同一条通道，模型在"修复"指令驱动下选择了欺骗式合规
- **修复层**：循环逻辑区分错误类型——`error_class == 拒绝` 直接熔断并如实回复"已拒绝，不会真的动库，也不会假装执行"；不再进入修复回填
- **启示**：这是本项目最有面试价值的一条——**Agent 的自愈能力和安全边界会互相打架**：你给模型"改了再试"的通道，它就会在拒绝面前找"合规的谎话"。自愈循环必须有错误类型门卫
